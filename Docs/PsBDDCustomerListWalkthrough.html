From a feature in plain words to tested, written documents

This walkthrough takes the Customer List example from a story on paper to a DUnitX fixture that tests it and writes the results to Markdown, HTML and PDF. Follow the same nine steps for each feature of your own application.

Plan the feature

Steps 1-2, before any code
1

Write the feature as a story

on paper, then as constants

Say who wants the feature, what they want and why. Note the requirement it satisfies, if you track requirements. These words go into the documents unchanged, so write them for the reader of the document, not for the compiler.

Fixture unit, implementation section
const
  CUSTOMER_DESCRIPTION = '''
    As a clerk
    I want to check whether a customer is in the customer list
    So that I do not create the same customer twice
    ''';
  CUSTOMER_REQUIREMENT =
    'The system shall report whether a customer is in the customer list.';

Tips

  • A multiline string literal (''', Delphi 12 and later) keeps the line breaks of the story.
  • Name constants in UPPER_SNAKE_CASE, as the framework and its examples do.
  • No requirement? Leave out WriteRequirement in step 4.
2

Write each scenario as Given, When, Then

on paper

One scenario is one example of the feature at work. Write its lines in the user's words. Each line becomes one step, and each step becomes one method of your fixture. Give each method a name that says what it does.

The two Customer List scenarios

Then the customer is found
And exactly one match is returned
Unknown customer is not found

When the clerk searches for "Brown"

Write the fixture

Steps 3-7, in CustomerList.Feature.Tests.pas
3

Declare the fixture class

interface section

One fixture describes one feature. It holds the feature writer, the state the steps share, one private procedure per step, and one [Test] method per scenario.

CustomerList.Feature.Tests.pas
unit CustomerList.Feature.Tests;

interface

uses
  DUnitX.TestFramework,
  PsBDD.Framework;

type
  [TestFixture]
  TCustomerListFeature = class
  private
    FFeatureWriter: IPsBDDFeatureDocumentWriter;
    FCustomers: TArray<string>;
    FMatches: TArray<string>;

    function FindCustomers(const AName: string): TArray<string>;

    // Steps
    procedure AListWithSmithAndJones;
    procedure SearchForSmith;
    procedure SearchForBrown;
    procedure TheCustomerIsFound;
    procedure ExactlyOneMatch;
    procedure NoCustomerIsFound;
    procedure TheListStillHoldsTwo;
  public
    [SetupFixture]
    procedure SetupFixture;
    [TearDownFixture]
    procedure TearDownFixture;

    [Test]
    procedure CustomerIsFoundInTheList;
    [Test]
    procedure UnknownCustomerIsNotFound;
  end;

implementation

uses
  System.SysUtils,
  PsBDD.FeatureWriter, PsBDD.MarkdownDocument, PsBDD.HTMLDocument;

Rules for step methods

  • Private procedures with no parameters and no return value.
  • Steps share state through private fields, here FCustomers and FMatches.
  • A step method can be reused by several scenarios.
  • FindCustomers is not a step. It stands in for the application code under test. In your project, call your real code instead.
  • Add only the document units you use to the implementation uses.
4

Describe the feature and choose the documents

SetupFixture

Create the feature writer, describe the feature, add a document for each output, then open them and write the feature. False makes a combined document that collects many features, with numbered headings and a table of contents.

Point at a line of code to see what it writes.

SetupFixture
procedure TCustomerListFeature.SetupFixture;
begin
  FFeatureWriter := TPsBDDFeatureDocumentWriter.Create;
  FFeatureWriter.Title := 'Customer list';
  FFeatureWriter.Description := CUSTOMER_DESCRIPTION;
  FFeatureWriter.Status := fsInDevelopment;
  FFeatureWriter.RequirementReference := 'REQ#014';
  FFeatureWriter.RequirementText := CUSTOMER_REQUIREMENT;

  FFeatureWriter.AddDocument(TPsBDDMarkdownDocument.Create(
    'C:\Docs\CustomerList.md', auTester, False));
  FFeatureWriter.AddDocument(TPsBDDHTMLDocument.Create(
    'C:\Docs\CustomerList.html', auBusiness, False));

  FFeatureWriter.Open;
  FFeatureWriter.WriteFeature;
  FFeatureWriter.WriteRequirement;
end;

5

Write one test method per scenario

[Test] methods

Each test method starts the scenario with BeginScenario and holds only the chain of steps. Every step takes the method to run and the line to write. The test reads like the scenario you wrote in step 2.

Point at a step line to find it in the document.

The two test methods
procedure TCustomerListFeature.CustomerIsFoundInTheList;
var
  Scenario: IPsBDDScenario;
begin
  Scenario := TPsBDDScenario.Create(
    FFeatureWriter.BeginScenario('Customer is found in the list'));
  Scenario
    .Given(AListWithSmithAndJones, 'a customer list with "Smith" and "Jones"')
    .When(SearchForSmith, 'the clerk searches for "Smith"')
    .&Then(TheCustomerIsFound, 'the customer is found')
    .&And(ExactlyOneMatch, 'exactly one match is returned');
end;

procedure TCustomerListFeature.UnknownCustomerIsNotFound;
var
  Scenario: IPsBDDScenario;
begin
  Scenario := TPsBDDScenario.Create(
    FFeatureWriter.BeginScenario('Unknown customer is not found'));
  Scenario
    .Given(AListWithSmithAndJones, 'a customer list with "Smith" and "Jones"')
    .When(SearchForBrown, 'the clerk searches for "Brown"')
    .&Then(NoCustomerIsFound, 'no customer is found')
    .But(TheListStillHoldsTwo, 'the customer list still holds 2 customers');
end;

  • Then the customer is found

Keep to these rules

  • One scenario per test method, held in a local Scenario: IPsBDDScenario. The status is written when the variable is released at end;.
  • Then and And are reserved words, so write .&Then and .&And. .But needs no &.
  • Need cleanup? Call .Teardown(...) first, before .Given.
  • To keep a technical scenario out of the business document, pass audiences: BeginScenario('...', [auTester]).
6

Write the step methods

private procedures

Given steps set up the state, When steps act, and Then, And and But steps check the result with DUnitX's Assert. A step fails when it raises, and only a step that asserts or raises can fail. Give every assert a message, because the message is written to the document when the step fails.

Step methods
procedure TCustomerListFeature.AListWithSmithAndJones;
begin
  FCustomers := ['Smith', 'Jones'];
  FMatches := nil;
end;

procedure TCustomerListFeature.SearchForSmith;
begin
  FMatches := FindCustomers('Smith');
end;

procedure TCustomerListFeature.SearchForBrown;
begin
  FMatches := FindCustomers('Brown');
end;

procedure TCustomerListFeature.TheCustomerIsFound;
begin
  Assert.IsTrue(Length(FMatches) > 0, 'Smith was not found');
end;

procedure TCustomerListFeature.ExactlyOneMatch;
begin
  Assert.AreEqual(1, Length(FMatches), 'Expected exactly one match');
end;

procedure TCustomerListFeature.NoCustomerIsFound;
begin
  Assert.AreEqual(0, Length(FMatches), 'Brown should not be found');
end;

procedure TCustomerListFeature.TheListStillHoldsTwo;
begin
  Assert.AreEqual(2, Length(FCustomers), 'The search changed the customer list');
end;

function TCustomerListFeature.FindCustomers(
  const AName: string): TArray<string>;
var
  LName: string;
begin
  // Stands in for the application code under test
  Result := nil;
  for LName in FCustomers do
    if SameText(LName, AName) then
      Result := Result + [LName];
end;
If TheCustomerIsFound fails
Scenario 1: Customer is found in the list
  • Given a customer list with "Smith" and "Jones"
  • When the clerk searches for "Smith"
  • Then the customer is found
Status: Failed - Condition is False when True expected. Smith was not found

What a failure does

  • The remaining steps do not run, so the And line is missing.
  • The document shows every step up to the failing one, then the message, in red.
  • The exception is raised again, so DUnitX reports the test as failed as usual.

Save the documents and register the fixture

TearDownFixture

Close saves every document and updates the table of contents. Call it yourself: if a file cannot be saved, Close reports the error. Register the fixture so DUnitX runs it.

End of the unit
procedure TCustomerListFeature.TearDownFixture;
begin
  FFeatureWriter.Close;   // saves CustomerList.md and CustomerList.html
  FFeatureWriter := nil;
end;

initialization
  TDUnitX.RegisterTestFixture(TCustomerListFeature);

end.

Wire up the project and run

Steps 8-9, in CustomerLookup.Tests.dpr
8

Set up the run in the project file

.dpr

The project file sets what happens to existing documents, registers the optional preambles and PDF, runs the fixtures, and makes the PDF once every fixture has saved its documents. Do this once per test project, not per fixture.

CustomerLookup.Tests.dpr
program CustomerLookup.Tests;

{$APPTYPE CONSOLE}

uses
  System.SysUtils,
  DUnitX.TestFramework,
  DUnitX.Loggers.Console,
  PsBDD.Framework,
  PsBDD.TMSPDF,
  CustomerList.Feature.Tests in 'CustomerList.Feature.Tests.pas';

var
  Runner: ITestRunner;
  Results: IRunResults;
begin
  TDUnitX.CheckCommandLine;
  TPsBDDRun.RunStart := rsOverwrite;
  TPsBDDRun.AddPreamble('C:\Docs\CustomerList.md',
    'C:\Docs\CustomerListPreamble.md');
  TPsBDDRun.AddPreamble('C:\Docs\CustomerList.html',
    'C:\Docs\CustomerListPreamble.html');
  TPsBDDRun.AddConversion(TPsBDDTMSPDFConversion.Create(
    'C:\Docs\CustomerList.md', 'C:\Docs\CustomerList.pdf',
    'Customer Lookup'));

  Runner := TDUnitX.CreateRunner;
  Runner.AddLogger(TDUnitXConsoleLogger.Create(True));
  try
    Results := Runner.Execute;
  finally
    TPsBDDRun.PerformConversions;
  end;
  if not Results.AllPassed then
    ExitCode := 1;

  if TDUnitX.Options.ExitBehavior = TDUnitXExitBehavior.Pause then
  begin
    Write('Done. Press <Enter> to quit.');
    Readln;
  end;
end.

RunStart: what happens to last run's document

rsAppendDefault. Adds this run to the end, building a history.
rsOverwriteStarts a new document each run. Used here.
rsArchiveRenames the old one with its date, then starts a new one.

Optional parts

  • Preamble: your own introduction to the application, at the top of a new combined document. Until the file exists, documents are written without one.
  • PDF: needs the TMS FNC Core add-on and PsBDD.TMSPDF. Leave out the conversion and that unit if you don't need a PDF.
  • Pause: set Run > Parameters to --exit:Pause to keep the console open when you run from the IDE.

Keep PerformConversions in the finally block

It must run after every fixture has closed its documents, and the PDF is still made when the runner raises. It never runs by itself.
